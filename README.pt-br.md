# Go Systems Challenges

🇺🇸 [English version](README.md)

![Go Version](https://img.shields.io/badge/Go-1.22%2B-00ADD8?logo=go)

Uma coleção de 22 challenges de Go autoproduzidos, em nível sênior, construídos pra aprofundar conhecimento prático de concorrência, network programming e padrões de sistemas distribuídos o tipo de problema que aparece em backends reais e em entrevistas técnicas de empresas focadas em infraestrutura.

Construí isso pra mim mesmo porque não encontrei material que fosse além de "assim funcionam goroutines e channels" e entrasse nos trade-offs que realmente importam em produção: granularidade de lock, backpressure, graceful shutdown, idempotência sob retry, consenso. Compartilhando caso seja útil pra outros engenheiros se preparando pro mesmo tipo de problemas e/ou entrevistas.

Cada pasta de challenge tem seu próprio README com o contexto do problema, o que de fato foi implementado, e as decisões de design relevantes. Os textos estendidos (enunciado do problema + esqueleto inicial, majoritariamente em português) ficam em [`README_FULL_NOTES.md`](./README_FULL_NOTES.md).

## Por que isso existe

A maioria dos materiais de concorrência em Go para no "assim funcionam goroutines e channels". Não tinha muito material que entrasse nos trade-offs que importam em produção: granularidade de lock, ordem de graceful shutdown, idempotência sob retry concorrente, consenso. Esse repo é o currículo que montei pra mim mesmo pra fechar essa lacuna - um problema de cada vez, cada um com aprendizados claros e, quando existe, uma suíte de testes que garante correção com `-race`.

| 24 | [UDP Confiável: Número de Sequência + ACK + Retransmissão](./24-udp_reliable_retransmit) | Networking | Camada de confiabilidade stop-and-wait em cima de UDP cru: toda mensagem carrega um número de sequência incremental, e o cliente retransmite o datagrama idêntico no timeout se nenhum ACK chegar; o servidor sempre reconfirma, mas rastreia números de sequência já vistos por endereço de cliente, então um duplicado retransmitido nunca é reprocessado, só reconfirmado, mantendo o protocolo idempotente sob perda de pacote tanto na requisição quanto na resposta. Análise e benchmarks de p50 e p99 |
| 25 | [Reescrita do Order Book: Skip List + Cancelamento com Lista Duplamente Encadeada](./25-order_book_skip_list_doubly_linked) | Data Structures & Systems Design | Reescreve o interior de uma matching engine baseada em heap pra uma skip list ordenada por preço (substituindo tanto o heap quanto o mapa preço-pra-pedidos por uma única fonte de verdade) mais uma lista duplamente encadeada por price level (substituindo uma slice, então cancelar um pedido em qualquer ponto da fila vira O(1) em vez de O(n)); documenta os trade-offs de design, incluindo por que deletar um elemento arbitrário de um heap força uma reconstrução O(n log n) que uma skip list evita. |
| 26 | [Packetizer Estilo RTP: Seq + Timestamp](./26-rtp_style_packetizer_seq_timeout) | Streaming / Networking | Implementa timeliness sobre UDP em vez de confiabilidade: cada datagrama carrega um número de sequência e timestamp sem ACK e sem retransmissão, já que um frame de áudio atrasado não vale nada depois que seu momento de playback já passou; o receptor detecta gaps e chegadas fora de ordem puramente pelo delta do número de sequência, evitando deliberadamente o padrão ACK/retry do challenge de UDP confiável, já que isso derrotaria o propósito do RTP. |
| 27 | [Jitter Buffer: Reordenação](./27-jitter_buffer_reordering) | Streaming / Networking | Reaproveita a skip list construída pro order book (mesmo insert O(log n) / front O(1), agora indexada por número de sequência em vez de preço) pra segurar pacotes estilo RTP fora de ordem até que chegue seu horário programado de liberação ou expire um deadline por pacote; um ticker esvazia o início da lista pra um channel de playback, então um pacote que nunca aparece é pulado em vez de travar o playback, e o player reconstrói os gaps de sequência esperada pra reportar perda definitiva e latência de playback. |
| 28 | [UDP FEC (XOR): Pacotes Sequenciados + Paridade + Reconstrução](./28-udp_fec_via_xor_seq_parity_packets) | Streaming / Networking | Adiciona correção de erro proativa (forward error correction) em cima do packetizer estilo RTP: o remetente faz XOR de cada grupo de tamanho fixo de pacotes de dado num pacote de paridade enviado junto, e o receptor reconstrói um único pacote faltante por grupo a partir dos sobreviventes mais a paridade, reportando perda definitiva só quando 2 ou mais pacotes do mesmo grupo estão faltando, já que paridade XOR simples não recupera mais de uma perda por grupo. |
| 29 | [Protocolo de Comunicação Inter-Réplica: WriteProposal/WriteAck/Heartbeat sobre Framing Reaproveitado](./29-inter_replica_p2p_communication_protocol) | Distributed | Constrói o canal de mensagens entre nós réplica do order book antes da lógica de quorum: reaproveita o framing length-prefix do stream broker pra uma conexão de peer simétrica (cada nó é discador e listener ao mesmo tempo, uma goroutine por peer pra leitura e escrita), trocando WriteProposal, WriteAck vazio, e Heartbeat sem payload; uma regra provisória de dial lexicográfico evita conexão duplicada entre pares de nós, até um handshake de identidade de verdade substituir isso. |
| 30 | [Identidade de Conexão + Teste de Integração + Spawn Multi-Nó: Identidade de Peer via Handshake](./30-multi_node_p2p_connection_identity) | Distributed | Substitui a identidade de peer baseada em RemoteAddr efêmero por um handshake bloqueante de MsgHello trocado antes de qualquer outro tipo de mensagem, permitindo que o cluster detecte e feche conexões duplicadas entre o mesmo par de nós por identidade real em vez de por convenção; validado com teste de integração baseado em net.Pipe (conclusão do handshake, registro correto no cluster, rejeição de duplicata) passando limpo sob -race, e confirmado ao vivo em 3 nós reais spawnados com heartbeat trafegando entre todos os pares. |
| 31 | [Quorum Write + Integração com o Orderbook: Comandos Replicados com Re-Match Determinístico](./31-quorum-write-orderbook-integration) | Distributed | Conecta o canal de replicação com o order book pela primeira vez: propostas ganham ID nodeAddr:counter, quorum é calculado como (len(peers)+1)/2+1 em vez de fixo, e um conjunto de votantes à prova de ack duplicado (mapa indexado por identidade do peer) rastreia cada proposta pendente; ao bater quorum, um MsgCommit broadcast faz todo nó (não só o proponente) aplicar o mesmo comando AddOrder/Cancel e rerodar o matching de forma determinística, validado de ponta a ponta em 3 nós reais com ordens cruzando entre nós diferentes e convergindo pro mesmo estado de book. |
| 32 | [Eleição de Líder Raft: Máquina de Estado Pura Separada do Transporte](./32-raft-leader-election-orderbook) | Distributed | Introduz um pacote raft independente (sem rede, testável isoladamente) com NodeState/CurrentTerm/VotedFor e uma única fórmula QuorumSize() compartilhada entre eleição e futura maioria de commit de log; o pacote cluster empilha timeout de eleição randomizado (150-300ms), RPCs RequestVote/VoteGranted, e um MsgLeaderHeartbeat exclusivo do líder mantido deliberadamente separado do heartbeat de liveness pré-existente, pra saúde de conexão do peer e liderança Raft nunca se confundirem. |

## Como rodar

A maioria dos challenges é um módulo Go independente. O padrão comum:

```bash
cd <pasta-do-challenge>
go run .              # ou `go run ./server` / `go run ./client` onde o código está separado
go test -race ./...   # nos challenges que têm suíte de testes
```

Alguns challenges expõem um `Makefile` com os targets `build`/`execute` em vez disso - confira o README de cada challenge pro comando exato. O `13_idempotent_payment_processing_postgresql` também precisa de uma instância PostgreSQL rodando.
